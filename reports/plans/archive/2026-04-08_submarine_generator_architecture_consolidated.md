# Sub3D - Submarine Generator Architecture Consolidated

Date: 2026-04-08
Status: architecture decision for First Playable submarine generation
Scope: generated submarine, runtime definition, flooding, stations, spawn points, airlock

---

## 1. Decision

The First Playable submarine is not a Blender mesh with manual gameplay volumes.

The First Playable submarine is the first product of a submarine generator.

The generator produces:

- a closed exterior hull mesh
- exterior collision
- interior walkable geometry
- straight bulkheads
- doors and hatches
- one explicit airlock
- generated compartments
- flood graph
- station slots
- crew spawn points
- runtime metrics

Runtime systems consume one generated product:

```text
USubmarineGeneratorSpec -> C++ generator -> USubmarineDefinition -> runtime components
```

`USubmarineDefinition` is the runtime source of truth.

The generated exterior hull mesh inside `USubmarineDefinition` is the physical truth for exterior collision, impacts, tunnel contact, and creature contact.

The generated compartment and flood data inside `USubmarineDefinition` are derived from the same generator pass as the mesh. They are not authored as a separate competing truth.

---

## 2. Why This Replaces The Current Patchwork

The current codebase has three competing submarine definition paths:

- `SubCompiler`: functional graph -> layout -> generated actor
- `Sub3DBake`: authoring asset -> compiled asset
- fallback layout: mesh or bounds -> single compartment

These paths do not match the target workflow. They make different systems answer the same question differently: what is this submarine, where are its rooms, where are its doors, and what floods?

The new rule is:

```text
One generated submarine definition. No runtime guessing. No fallback submarine.
```

Old systems can remain compilable during migration, but they do not define the FP submarine.

---

## 3. Non-Negotiable Invariants

1. The exterior hull mesh generated by the pipeline is closed.
2. Exterior collision is generated from the generated hull, not from hand-placed gameplay volumes.
3. The player can leave the submarine only through explicit access modules: airlock, hatch, or later equivalent modules.
4. The airlock is a real flood volume between interior and exterior.
5. Opening the exterior airlock door floods the airlock. It does not flood the whole submarine while the interior airlock door is closed.
6. The player does not place arbitrary freeform interior walls in this phase.
7. The player/design pass places straight bulkheads, doors, stations, and spawn requests.
8. Compartments are derived from bulkheads, decks, and access modules.
9. Flooding is simulated per generated compartment and through generated graph edges.
10. `SubHullComponent` remains damage-only after migration. Flooding moves to `USubFloodComponent`.
11. `BreachVfxManagerComponent` continues to read `SubHullComponent` damage data.
12. No fallback layout is allowed in the FP generator path.

## 4. Authoring And Runtime Objects

### 4.1 `USubmarineGeneratorSpec`

Editor-facing input for the generator.

It contains designer intent:

- hull length, width, height
- section profile, superellipse exponent, width-to-height ratio
- bow profile and stern profile
- wall thickness
- floor clearance rules
- deck count request
- bulkhead X positions
- door and hatch requests
- airlock request
- station requests
- spawn requests
- flood tuning defaults

This asset is simple enough to edit in the Unreal editor before a full submarine editor exists.

### 4.2 `USubmarineDefinition`

Generated runtime product.

It contains:

- generated exterior mesh sections
- generated interior mesh sections
- generated collision mesh data
- base mass
- submerged volume
- generated compartments
- generated connections
- generated flood graph
- generated station slots
- generated spawn points
- generated damage mapping data
- flood config
- validation report

Runtime components read this asset. They do not read `USubmarineGeneratorSpec`.

---

## 5. First Playable Target

The FP submarine is deliberately small.

Target:

- one generated submarine
- one deck
- four to six compartments
- one airlock
- helm station
- engine station
- ballast station
- sonar station or helm-bound sonar
- crew spawn point
- one scripted breach path
- one pump path
- one interior door transfer test

Example compartment order:

```text
Bow -> Helm -> Main -> Engine -> Stern -> Airlock
```

This is enough to validate:

- closed hull collision
- interior traversal
- door state
- airlock flooding
- breach flooding
- pump behavior
- water mass affecting movement
- crew water-height detection
- damage bridge from hull breach to compartment inflow

## 6. Reuse From Existing Code

`SubCompiler` is not reused as the final architecture. It is reused as a C++ toolbox.

Reuse assessment:

| Existing code | Reuse | Action |
| --- | --- | --- |
| `USubmarineEnvelopeDef` | High | Keep math and profile parameters. |
| `SubmarineGeometryBuilder` exterior mesh | Medium-high | Reuse and harden closed hull output. |
| `SubmarineGeometryBuilder` interior mesh | Medium | Reuse for one-deck interior, then simplify contracts. |
| `SubmarineGeometryBuilder` bulkhead mesh | Medium | Reuse cutout logic, validate doors and collision. |
| `SubmarineLayoutSolver` | Medium | Rework around bulkheads as primary cuts. |
| `SubmarineBuildCompiler` | Low-medium | Replace `USubmarineLayoutAsset` output with `USubmarineDefinition`. |
| `SubCompilerTypes.h` | Medium | Reuse ideas, do not expose directly in runtime definition. |
| `Sub3DBake` | Low for FP | Parked. Not part of FP generation path. |
| fallback layout | None | Remove from FP path. |

## 7. Generation Pipeline

### 7.1 Hull Envelope

Input:

- length
- width
- height
- section profile
- superellipse exponent
- bow/stern taper
- wall thickness
- kiosk request

Output:

- closed exterior hull mesh
- exterior collision data
- hull bounds
- approximate volume
- base mass proxy
- damage surface mapping candidates

Validation:

- mesh has no open ends
- bow and stern caps are closed
- collision exists
- dimensions match the generator spec

### 7.2 Interior Space

Input:

- hull envelope
- wall thickness
- floor clearance rules
- deck count request

Output:

- walkable floor mesh
- interior wall mesh
- valid local interior volume

Rules:

- one deck for FP
- second deck is generated only when height and clearance allow it
- floor does not extend outside interior hull
- bow and stern cuts stay valid and traversable

### 7.3 Bulkheads And Doors

Input:

- bulkhead X positions
- door requests
- hatch requests

Output:

- bulkhead mesh
- door cutouts
- collision for sealed areas
- connection definitions

Rules:

- bulkheads are perpendicular to the X axis for this phase
- doors are rectangular cutouts
- door bounds must fit inside the generated bulkhead profile
- sealed bulkheads block traversal and water
- open or doored bulkheads create flood graph edges

### 7.4 Compartments

Input:

- interior space
- bulkheads
- airlock module

Output:

- generated compartment list
- bounds
- capacity liters
- max water height
- walkable floor Z
- room tags
- later: height-volume curve

Rule:

```text
Segment between two valid boundaries = one generated compartment.
```

For FP, capacity can be computed from an approximate integrated cross-section. The simple bounding-box capacity used by older code is not the final source of truth.

### 7.5 Airlock

Input:

- airlock request
- exterior access transform
- interior target compartment

Output:

- airlock chamber compartment
- inner door connection
- exterior door connection
- exterior flood edge
- station/interaction sockets for doors

Rules:

- airlock is a real compartment
- exterior edge connects only to the airlock chamber
- interior door closed blocks flood from airlock to main submarine

### 7.6 Flood Graph

Input:

- generated compartments
- generated connections
- airlock exterior edge
- breach mapping data

Output:

- `FCompiledFloodGraph`
- connection list for runtime door state

Runtime rule:

```text
Water flows through graph edges. No runtime topology scan.
```

### 7.7 Stations, Spawns, And Sockets

Input:

- station requests
- spawn requests
- generated compartments
- interior clearance data

Output:

- generated station slots
- crew spawn points
- repair target sockets
- optional debug sockets

Validation:

- station slot is inside a compartment
- station footprint does not overlap a bulkhead
- station has a valid facing direction
- crew spawn is inside walkable interior space

## 8. Runtime Components

### 8.1 `USubFloodComponent`

New flooding authority.

Responsibilities:

- initialize from `USubmarineDefinition`
- own replicated compartment water state
- own replicated breach-to-flood state
- own door state or bridge door state during migration
- simulate breach inflow
- simulate transfer through open connections
- simulate pumps
- broadcast `OnCompartmentFloodUpdated`

Simulation:

```text
1. Apply breach inflow to target compartments.
2. Transfer water through open graph edges using water-height delta.
3. Apply pumps.
4. Update water height, normalized water level, and free air.
5. Broadcast compartment flood state.
```

### 8.2 `USubHullComponent`

Remains damage-only after migration.

Keeps:

- sheet/cell damage model
- impact projection
- breach clustering
- flow field generation for VFX and suction feedback
- damage delegates

Stops owning:

- compartment water state
- pump state
- flood propagation
- fallback layout

Bridge:

```text
SubHullComponent::OnBreachesUpdated
  -> USubFloodComponent maps breach local point to generated compartment
  -> USubFloodComponent creates or updates breach inflow
```

### 8.3 Existing Systems To Rewire

| System | New flood dependency |
| --- | --- |
| `SubMovementComponent` | water mass from `USubFloodComponent` |
| `SubCrewCharacter` | compartment sample from `USubFloodComponent` |
| `FloodWaterVisualsComponent` | `OnCompartmentFloodUpdated` from `USubFloodComponent` |
| `DoorFloodVfxComponent` | door state and compartment water from `USubFloodComponent` |
| `SubmarineFeedbackDirectorComponent` | flood delegates from `USubFloodComponent`, damage delegates from `USubHullComponent` |
| `SubmarineSystemsComponent` | pump commands to `USubFloodComponent` |
| `SubmarineCompartmentComponent` | temporary facade over `USubFloodComponent` |
| `BreachVfxManagerComponent` | unchanged, reads `USubHullComponent` |

## 9. Implementation Plan

### Phase A - Data Foundation

Create:

- `Source/Sub3D/Submarine/SubmarineGeneratorSpec.h`
- `Source/Sub3D/Submarine/SubmarineDefinitionTypes.h`
- `Source/Sub3D/Submarine/SubmarineDefinition.h`

Rules:

- no include of `SubmarineLayoutAsset.h`
- no include of `SubCompilerTypes.h` in runtime definition types
- shared runtime types are explicit and local to the new contract

### Phase B - Generator Product

Create or refactor a generator service:

- input: `USubmarineGeneratorSpec`
- output: `USubmarineDefinition`

Implementation:

- reuse `USubmarineEnvelopeDef` math
- reuse mesh generation routines where they match the new contract
- replace `USubmarineLayoutAsset` output
- produce a full `USubmarineDefinition`

### Phase C - Flood Runtime

Create:

- `Source/Sub3D/Submarine/SubFloodComponent.h`
- `Source/Sub3D/Submarine/SubFloodComponent.cpp`

Add:

- initialization from `USubmarineDefinition`
- replicated compartment states
- breach states
- door state APIs
- pump APIs
- compartment query APIs
- damage bridge listener

### Phase D - Runtime Wiring

Modify:

- `SubmarineBase.h/.cpp`
- `SubMovementComponent.cpp`
- `SubCrewCharacter.cpp`
- `FloodWaterVisualsComponent.cpp`
- `DoorFloodVfxComponent.cpp`
- `SubmarineFeedbackDirectorComponent.cpp`
- `SubmarineSystemsComponent.cpp`
- `SubmarineCompartmentComponent.cpp`

Keep:

- `BreachVfxManagerComponent` unchanged
- `SubDoorActor` on facade until all door state calls are migrated
- old tests until replacement tests exist

### Phase E - Generator Completion For FP01

Produce:

- one FP submarine generator spec
- one generated `USubmarineDefinition`
- one generated or spawned runtime actor

Validate:

- closed exterior hull
- walkable interior
- bulkhead doors
- airlock behavior
- station slots
- crew spawn
- flood graph
- damage bridge

### Phase F - Deprecation

Mark legacy:

- `SubmarineLayoutAsset`
- fallback layout path
- old `SubCompiler` actor output path
- `Sub3DBake` FP usage

Do not delete until the new path compiles and the FP submarine runs in PIE.

## 10. Verification Checklist

Compile:

- project builds without C++ errors

Generator:

- generator creates `USubmarineDefinition`
- exterior mesh has vertices, triangles, and closed caps
- collision mesh exists
- compartments exist and cover expected interior segments
- airlock chamber exists
- flood graph has one volume per compartment
- flood graph has valid door edges
- flood graph has an exterior edge only where intended

Runtime:

- `SubFloodComponent` initializes from definition
- `SetCompartmentFloodDirect` raises visible water
- `CreateBreach` raises water automatically
- opening a door transfers water
- closing a door blocks water
- opening exterior airlock door floods only the airlock when the inner door is closed
- pump reduces water
- `SubMovementComponent` receives flooded mass
- `SubCrewCharacter` detects water height in the current compartment
- clients see replicated water state on listen server

Damage bridge:

- hull impact creates `SubHullComponent` breach cluster
- breach cluster maps to the expected generated compartment
- `USubFloodComponent` creates inflow from the cluster
- breach VFX still uses `SubHullComponent`

---

## 11. Deferred

Deferred until FP submarine is stable:

- arbitrary interior wall placement
- full player-facing submarine editor
- multi-deck authoring UX
- complex freeform hull sculpting
- dynamic interior navmesh for creatures
- bulkhead destruction with complete geometry rebuild
- distance-field water rendering as the first implementation
- Sub3DBake integration

Distance-field or SDF water rendering remains a rendering upgrade. The simulation contract remains compartment water amount plus generated volume data.

---

## 12. Summary

The new architecture is not a fourth patch on top of the old systems.

It is a single generated submarine contract:

```text
USubmarineGeneratorSpec
  -> C++ generator
  -> USubmarineDefinition
  -> SubHull damage, SubFlood water, stations, doors, spawns, visuals, movement
```

The FP submarine validates this contract before a player-facing submarine editor is built.
